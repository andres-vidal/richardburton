# Publication history

A publication's mutation log, newest first: each entry names the action
(created / updated / deleted / restored / merged / unmerged / renamed /
distinct / reopened), the acting user, and the date, and
**updates state exactly what changed**: scalar fields as `old → new`, and
sources as the precise entries added (+) and removed (−) — or a reorder, when
the same entries merely moved.

The data comes from the append-only `publication_history` log
(`GET /publications/:id/history`, admin-only). The server computes each diff
against the previous version of that record and sends it **structurally** —
field keys and raw values, no labels — and the data layer turns that into
labelled, ordered changes on the way in (`presentChanges`). So this component
never diffs anything: it renders `entry.changes` as given. The
[publication detail](?path=/docs/publications-publication-detail--docs) shows it
to admins in a collapsed "History" section, with the entries read together with
the record.

Styling is quiet here, with no frame around an entry, smaller type and compact
badges, because the log is a supporting detail of the publication it belongs
to. The standalone
[history feed](?path=/docs/publications-publication-history-feed--docs) renders
the same entries as full cards, where they _are_ the page's subject.

## Props

- `entries` — the log, newest first, each entry with the `changes` that
  `withChanges` in `modules/publication/history` gives it.

## States

- **Default** — the stream above: a full lifecycle whose updates carry exact,
  attributed diffs (a retitle, a source added, that source later replaced)
  and no diff rows for delete/restore (nothing changed field-wise).
- **Empty** — records created before the history log exist have no entries;
  the absence is stated rather than hidden.

<Canvas of={PublicationHistoryStories.Empty} />

- **Without a baseline** — a change is described by comparing a record against
  the entry before it, so a log that opens on an update has nothing to compare
  against. That happens to records loaded straight into the database rather than
  entered through the app; `mix rb.backfill_history` gives those a starting
  point, and the entries already recorded without one say so.

## Renamed

A renamed entry records a name corrected in
[names management](?path=/docs/admin-names--docs), on each
publication that credits the name. It shows the change like an update, but it
has no undo: the name changed for every publication at once, so it is changed
back in names management, and the entry says so.

## Duplicate decisions

When a duplicate reviewer rules publications apart, each of them records a
distinct entry naming the others, by title, year and translators. Putting them
back in the review records a reopened entry the same way. A decision changes no
field and has no undo here: it is taken back in the duplicate review.

## Comments

A change to the comments lists them before and after, each rendered from its
Markdown with [`Comments`](?path=/docs/publications-comments--docs), and
"(none)" for a side that had none. A merge lists the comments of each record it
took in with the rest of that record.
