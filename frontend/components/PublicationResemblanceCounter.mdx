# Resemblance counter

How many rows of an import look like a publication already known, and the way
into them. It sits in the workspace footer beside the
[error counter](?path=/docs/publications-publication-error-counter--docs).

The composite key already rejects a row that repeats a stored record exactly.
What this catches is the near-miss it cannot: a typo, a dropped accent, a
translator entered as "R. Burton" once and "Richard Burton" the next time. Left
alone those rows import cleanly and turn up later in the
[duplicate review](?path=/docs/publications-duplicate-review--docs), after they
are already in the database.

A row is measured against two things: the stored records, and the other rows of
the same import. The second half matters because a CSV can hold its own
near-duplicates, and neither of them is in the database for the review to find.

## It counts, it does not ask

The rows are measured as they are edited, the way they are validated — nothing
has to be pressed. `CheckResemblances`, mounted by the workspace, watches the
fields a resemblance is measured on and re-runs the check half a second after
they settle. Editing a year or a country changes no answer, so it asks nothing.

The whole set goes over each time rather than the row that changed, because a
row is measured against the others as well as against the database: editing one
row can make it the twin of another, and neither is stored for a query to find
them by. That is the expensive half, and it grows with the square of the rows —
see `Publication.Duplicates.resemblances/1`.

An edited row drops what it resembled straight away rather than keeping an
answer about values that have changed, so the count falls and then comes back.

## States

- **Found** — the count, and the way into the review.
- **Nothing alike** — no control at all. A look-alike is a question to answer,
  and no question is not news; the error counter is what says a set is in good
  order.
- **Answering lowers it** — keeping or discarding a row takes it out of the
  count.

The review itself is rendered whatever the count, because answering the last
question takes the count to nought while the review is still open, saying so.

## The row is a way in too

A row marked "this resembles something" without saying what leaves the reader to
go and find it, so the row carries its own control: it names the records by
title and year, says how many other rows of the import it matches, and opens the
review on that row rather than at the top of the queue.

It sits at the end of the row, beside sources, rather than in the leading cell.
That cell is the row's selection handle and is 2.5rem wide around a 1.25rem
icon, so a control there takes the clicks meant for selecting the row.

Which question the review is on therefore lives in the store rather than in this
control, since this is no longer the only thing that opens it — and that is also
what closes a review of rows the working set no longer holds.

## Following a record out

Each stored record in the review links to its own page, in a tab of its own: the
reader is in the middle of a queue of questions, over a workspace of rows that
nothing has saved yet.

## What it is not

A look-alike is not an error. It does not make a row invalid and it does not
hold back a submit: two editions of one book resemble each other and are both
worth having. Nothing is written either — a row has no id yet, so there is no
pair to rule apart the way the duplicate review does.
