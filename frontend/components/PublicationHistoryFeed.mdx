# Publication history feed

The database-wide mutation log, newest first — the admin "History" page.
Each entry names its publication, the action, the acting user, and the date;
updates carry the same exact field-level diffs as the
[per-record history](?path=/docs/publications-publication-history--docs).
Because the feed interleaves records, diffs are computed **per publication** —
an update is compared against that record's previous version, wherever it sits
in the feed. The server does that pairing and sends each diff with its entry, so
the feed cannot get it wrong by reading the row above.

Every entry the server marks `undoable` carries an **Undo**, which names the
entry (`POST /publications/:id/history/:version/undo`) and lets the server work
out the rest: a record's latest entry is always reconcilable (restore for a
delete, delete for an import or restore, revert for an update), as is **any
older update whose fields are untouched since** — reverted field by field, so
later changes to others survive. Older deletes (already negated by a restore)
and older imports/restores (undoing them would discard the edits that followed)
are settled history.

That rule lives on the server rather than here, which is what makes it binding:
the endpoint refuses an entry it cannot reconcile instead of trusting the
caller. Undo writes a _new_ history entry — the log is append-only and never
rewritten — so every undo is itself undoable from this feed, and no
confirmation gates stand in the way. **One at a time:** while a request is in
flight the pressed row spins and every other Undo goes disabled, so a refused
click looks refused.

**Filters**, a toggle button per action and a text that matches the title or
the user, narrow what is _shown_, never what diffs or undoability are computed
against. They are view
state, not navigation: what is _currently_ deleted lives on its own
[Deleted publications](?path=/docs/publications-deleted-publications--docs)
page, because a log of deletion _events_ answers a different question than the
set of records presently in the trash.

## Props

- `entries` — the log, newest first, read where the page is rendered from the
  admin-only `GET /publications/history`.
- `onUndo(entry)` — undoes an entry and returns whether it succeeded. It
  defaults to `undo` in `modules/publication/remote`. After a success the page
  is read again, so the new entry and the new undoable flags appear.

## States

- **Default** — interleaved streams; per-record diffs; undo wherever the
  action is still reconcilable.
- **Filtered by action** — chips narrowing the view.
- **Text filter** — narrowing by title or acting user.
- **Renames** — one item per rename, naming the old and the new name and
  linking to each publication it changed (below).
- **Empty** — a fresh log states its emptiness.

## Renames

A rename in [names management](?path=/docs/admin-names--docs) records an
entry on every publication that credits the name, but the server sends the
whole rename as **one entry**: the newest of them, whose `others` are the
other publications the rename changed and whose `nameChange` covers them all.
The feed shows it as one item about the name, not about a publication. Its
heading names the role, taken from the fields the name changed in (publisher,
translator, original author, or simply name when it changed in more than one
role), with the name before and after. It lists every publication the rename
changed, each linking to its page, and it has no Undo. The text filter finds a
rename by the title of any of those publications.
