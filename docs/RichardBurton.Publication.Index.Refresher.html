    RichardBurton.Publication.Index.Refresher (richard_burton v0.1.0)

    Rebuilds the materialized views the index reads: flat_publications, the flat rows the index lists, and search_documents and search_keywords, which are built from them. A write calls refresh/0 once for each operation, such as a bulk insert or an update, after it commits.

    The strategy comes from config :richard_burton, :search_index_refresh:

    • {:debounced, ms} (the default, used in dev and prod): the signals of a burst coalesce, and the views are rebuilt once after ms milliseconds with no signal, outside any transaction, with REFRESH MATERIALIZED VIEW CONCURRENTLY, so neither a search nor a write waits for the rebuild. A search includes a write up to ms milliseconds after it.
    • :sync_concurrent (e2e): rebuild inline before refresh/0 returns, with the same CONCURRENTLY refresh production runs, so an end-to-end test reads what it just wrote.
    • :sync (test): rebuild inline with a plain REFRESH, because the ExUnit sandbox runs each test in a transaction, where CONCURRENTLY is not allowed.

    In debounced mode the refresher also rebuilds once on boot, covering signals lost to a restart and data seeded while the app was down.

    refresh()

    Signal that the index is stale. Returns after the rebuild in sync modes.

    start_link(opts)

    Starts the refresher, registered under opts[:name], __MODULE__ by default, or unregistered when the name is nil. opts may also give :debounce_ms, the quiet window, :rebuild, the function that rebuilds the views, and :refresh_on_boot, whether to rebuild once on start.
