    RichardBurton.Publication.History (richard_burton v0.1.0)

    The append-only log of changes to publications. Each row records one change to one publication: the action, a flat snapshot of the publication after it, the actor, and a version that numbers the publication's entries in order.

    The database keeps the log append-only: a trigger rejects every UPDATE and DELETE on the table (see the migration SoftDeletePublications). Every change goes through the RichardBurton.Publication functions, or through RichardBurton.Vocabulary.rename/5 for a change of name, and each records its entries inside the transaction that makes the change. So a change and its entries commit or roll back together.

    Terms used here:

    • stream — the entries of one publication, newest first.
    • head — the latest entry of a stream that is not a decision. See head/1.
    • others — the other publications an entry is about, each with its snapshot when the entry was recorded. The entry's action says how they are involved: a merge absorbed them, an un-merge gave them back, a decision is about them, or the same rename changed them. A rename's entries are stored without them, and of/1 and all/0 read them from the rename's other entries. An entry of any other action has none.
    • absorbed — the state of a publication held inside another by a merge. A "merged" entry is on the publication that survived the merge, and names the publications it absorbed in its others. An "unmerged" entry names the ones it gave back. See absorbed/1.
    • decision — a duplicate reviewer's answer about publications that look alike, recorded by RichardBurton.Publication.Duplicates. A "distinguished" entry records that the publications are not the same record twice, and a "reconsidered" entry that the answer was taken back. Each publication the decision is about gets an entry, which names the other publications in its others. A decision changes no field, so its entry has no diff. It is not undone from the history, and head/1 and undoable?/3 skip it, so it does not stop the entries before it from being undone.

    A "renamed" entry records a change of name made in names management, on each publication that credits the name. It is diffed like an update, but it is not undone from the publication's history. Renaming the name again takes the change back for every publication at once. A fold of one name into another is recorded the same way, so the log does not tell the two apart.

    Terms for renames:

    • rename — the "renamed" entries that one call of RichardBurton.Vocabulary.rename/5 recorded, one for each publication it changed. They share a rename_id that no other rename has. all/0 returns each rename as one entry.
    • name change — what a rename changed in the fields that hold names, authors, original_authors and publishers: for each of those fields that changed, the names removed, under from, and the names added, under to. A rename onto a free name removes the old name and adds the new one. A fold into a name that a publication already credits only removes the old name, so to is empty for that publication. See annotate/2.

    Functions

    absorbed(ids)

    @spec absorbed([pos_integer()]) :: MapSet.t(pos_integer())

    Returns the ids among ids of the publications that are absorbed now.

    A publication is absorbed when the latest "merged" or "unmerged" entry that names it in others is a "merged" one. That entry is in the stream of the publication that survived the merge, not in the absorbed publication's own stream. The query reads only the ids that others holds, and at most one entry for each of ids.

    all()

    Returns every entry in the log, newest first, annotated by annotate/2, with each rename as one entry.

    The entry that stands for a rename is the rename's newest entry, in the place of that entry. Its others hold the other publications the rename changed, each with the snapshot of its own entry, and its name_change covers every entry of the rename: each field that any of them changed, with every name removed and every name added, each once and sorted. Entries of every other action are returned as they are.

    It reads the log with one query. The publications that are absorbed are found from the merge and un-merge entries among the ones it read.

    annotate(entries, absorbed)

    Sets the diff, undoable and name_change fields of each entry, and returns the entries in the order given. entries come newest first within each publication's stream, and may hold the streams of several publications, interleaved. absorbed holds the ids of the publications that are absorbed.

    An update, a rename, a merge and an un-merge get a diff, which compares the entry's snapshot with the snapshot of the next older entry in its own stream. It holds fields, each changed field with its value from before and to after, and sources, the sources added and removed, or nil when the sources did not change. Every other entry, and the oldest entry of a stream, gets a nil diff.

    An entry is undoable when undoable?/3 says so, and never while its publication is absorbed, because only undoing the merge gives that publication back.

    A rename's entry gets its name change (see the module doc), computed from its diff. It is nil when the diff is nil or changed no field that holds names. Every other entry gets a nil name change.

    Examples

    An update and the import before it, newest first:

    iex> alias RichardBurton.Publication.History
iex> [update, import] =
...>   History.annotate(
...>     [
...>       %History{publication_id: 1, version: 2, action: "updated", snapshot: %{"title" => "New"}},
...>       %History{publication_id: 1, version: 1, action: "created", snapshot: %{"title" => "Old"}}
...>     ],
...>     MapSet.new()
...>   )
iex> update.diff.fields
%{"title" => %{from: "Old", to: "New"}}
iex> {update.undoable, import.diff, import.undoable}
{true, nil, false}

    The update is the head, so it is undoable. The import has no older entry to compare with, and it is not undoable once a later entry exists.

    undoable?(entry, previous, head)

    Returns whether undoing entry would leave its publication as if the entry had never happened, with every later change kept. previous is the entry before it in its stream, or nil, and head is the stream's head (see head/1).

    • The head is undoable. The action that undoes it applies directly: a restore undoes a delete, a delete undoes an import or a restore, and an update is reverted.
    • An older update is undoable while the publication is not deleted and every field the update changed still holds the value it set. Undoing it then changes only those fields, and keeps later changes to the others.
    • An older entry of any other action is not undoable. A later restore already undid an older delete, and undoing an older import or restore would discard the changes that followed it. A merge or an un-merge changes several publications at once, and the changes after an older one were made to the merged publication.
    • A rename is not undoable. It changed a name for every publication that credits it, and renaming the name again takes it back.
    • A decision is not undoable. It is taken back in the duplicate review.
